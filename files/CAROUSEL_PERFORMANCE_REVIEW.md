## Exact evidence

1. **Complete names avoid explicit enumeration; clipped names do not.** `source/launcher_indexed_name.h:13-47` copies an unflagged name directly, with capacity checks. `source/ezkernelnew.c:7945-7965` uses it for normal SD ROMs; folders use it at 7907-7929. `Launcher_ResolveIndexedName` at 7856-7867 delegates to `Launcher_ResolveDirectoryEntry` at 3840-3896. The latter opens the directory and continues `f_readdir` after finding the match, checking for ambiguous identities until EOF. One clipped incoming title therefore costs D returned directory entries plus the EOF call in the normal successful case (and path traversal to open the directory), not merely the entries before the match. D includes entries other than displayed games. Keeping ambiguity/error checks is intentional safety behavior. Recents instead call `Launcher_ResolveFullPath` at 7933-7943, repeating component resolution; do not generalize ordinary-folder fast-path claims to recents.

   Records have 100-byte display-name arrays (`source/ezkernel.h:9,22`). `Launcher_CopyIndexedName` at 510-531 sets `FM_ENTRY_ALIAS_DISPLAY` when source length is **>=99 bytes**, and performs the existing CP936 boundary adjustment. Thus exactly 99 ASCII bytes also take the resolver path although they fit with NUL. This is a small conservative boundary inefficiency, not an explanation for 60 ordinary titles. Do not blindly change >= to >: flag semantics also affect display disambiguation (`ezkernelnew.c:1942`) and the CP936 clipping rule. Full aliases are retained by `Launcher_StoreFileRecord`, and identity selection prefers `altname` (535-554). Never resolve artwork from a clipped display prefix or use a hash alone as identity.

2. **Short names still encounter linear FAT directory lookup.** `source/ff15/ff.c:2384-2455` (`dir_find`) calls `dir_sdi(dp, 0)` then advances directory entries until match/end. `follow_path` calls it per component (3051,3095); `f_open` follows the path at 3742. Successful late-position opens are O(directory slots traversed); missing final names scan the entire containing directory. LFN entries add slots. Disk-sector reads may be cached, so entries traversed are not equivalent to SD reads. Using an SFN for a ROM open may reduce LFN comparisons but does not eliminate this linear search.

3. **Artwork precedence and repeated misses multiply opens.** `Launcher_LoadThumbnailForPath` at 6446-6492 tries mirrored artwork, CUSTOM/name, GBA game code (known code or header), then CUSTOM/extension, then built-in NOTFOUND. Preserve precisely this order and CUSTOM origin metadata. `Launcher_LoadMirroredThumbnail` at 6338-6388 tries canonical LFN directory first and legacy alias directory second if different. A missing artwork file in an existing large mirrored directory incurs a full search on each new incoming title. A missing parent directory instead stops at that parent's lookup; do not attribute every miss to the ROM folder's size.

   `Launcher_LoadThumbnailFromRomHeaderPath` at 6420-6439 opens the ROM, seeks 0xAC and reads four bytes before game-code art lookup. Ordinary SD entries pass no known code (7876,7964); unlike the ten virtual slots, their codes are not retained here. Thus GBA fallback reopens a ROM on each incoming cache miss, searching the ROM directory even for short indexed names. `Launcher_LoadExtensionDefaultThumbnail` at 6394-6417 directly opens CUSTOM/<extension>.bmp every time fallback reaches it, including repeated failure for the same extension. In a steady-state short-name GBA case with one mirror path, no matching custom hash, valid ROM code but missing code and extension artwork, there are four f_open attempts per incoming title: mirror BMP, ROM, code BMP, extension BMP. Two mirror candidates add one; a matching custom hash with failed file load adds another. This is a conditional source-derived count, not measured hardware data.

4. **Directory-path resolution is already positively cached.** `Launcher_ResolveArtworkDirectoryPath` at 3913-3932 caches the last successful source directory. Consecutive normal-folder loads do not re-enumerate every ancestor. Failures are not cached and alternating recents directories miss this one-entry cache. This cache resolves the ROM directory's LFN path, not existence of its artwork mirror. Do not claim it suppresses artwork f_open searches.

5. **CUSTOM manifest is bounded, but searched linearly.** `Launcher_LoadCustomThumbManifest` at 6019-6062 scans once per style, up to 256 entries (`LAUNCHER_CUSTOM_THUMB_MANIFEST_MAX`, line 145). `Launcher_ShouldTryCustomThumbnail` at 6064-6086 then compares up to M hashes for every custom candidate, M<=256. This is O(M) CPU work, not a repeated directory scan and not inherently a function of the active ROM folder's count. Hash match gates an exact filename open; hash collisions cause attempts, not authorization to substitute another title. The cap can omit custom images beyond 256; no 60 boundary follows from it. Initial manifest scan is a cold cost distinct from steady scrolling.

6. **Adjacent cache shift is bounded and preserves incoming data.** `Launcher_ShiftThumbCache` at 8470-8591 rebuilds only for invalid pointers/center or a non-adjacent requested index. Otherwise it moves two fixed image buffers and loads the newly exposed neighbor. Animation (`source/carousel_motion.h:428-501`) loads the incoming image before the five rendering frames, reuses any matching resident triplet entry, then marks incoming ready. `Launcher_MotionLoadIncoming` at 545-561 consumes matching ready data without another disk load, including valid missing-art state, and clears readiness. Successful animated adjacent motion therefore does not load incoming art twice. Animations off load the new neighbor through the fallback loader once. Small wrapped folders can reuse an existing image during animation. A three-slot cache necessarily reloads an evicted neighbor when reversing direction; that is bounded-cache churn, not demonstrated invalidation error.

   Full build at `ezkernelnew.c:8415-8469` loads up to three slots. Normal adjacent and wrapped navigation use Shift (15442-15483; matching horizontal branch 15536-15577). Pointer checks at 6670-6684 are fixed-address checks, not count-dependent. Reset at 7815 clears caches/workspace; no call was found on ordinary adjacent movement. Repeat delay at 8594-8626 depends on view, animation, recents and edge/completeness, not a >60 test. Initial directory enumeration/sorting at 14610-14652 occurs on directory refresh, not inside Shift.

7. **Image payload is fixed by style, not folder size.** Width/height/read size at 974-986 give 19,254 bytes for title BMPs and 12,854 for box BMPs. Read/transparent tagging at 6180-6210 adds fixed pixel work per successful load; file search before those reads still scales. Border rendering is outside this report's ownership and must retain the confirmed rollback.

## Small candidate changes, ordered by safety/scope

Integration follow-up: owner proposes sorted CUSTOM hash membership. Of the implementation options below, this is the safest behavior-preserving experiment: no new cache lifetime or negative-result semantics. Preserve duplicate/hash-collision membership, manifest cap and exact-path verification. Its benefit is bounded CPU comparisons, not proven relief of the ROM-folder-size symptom. Sent this recommendation directly to the integration thread. Owner also requested additional test files; deferred those to owner because the user's explicit ownership remains this report only.

- First add operation-count evidence in the integration owner's host harness. The ordinary indexed-name optimization is already present; do not implement it again or remove ambiguity scanning globally.
- If repeated extension misses are material, add a tiny bounded negative-result cache keyed by style, normalized extension and directory/session generation. Cache only definite absence (FR_NO_FILE/FR_NO_PATH), never generic read, close, media or corruption errors. Clear at directory refresh and relevant settings/media changes. This removes an identical full CUSTOM lookup per fallback title while preserving artwork order and full title identity. It changes when newly added files become visible, so define refresh behavior explicitly. Prefer metadata-only absence caching over reserving another image buffer.
- If clipped names dominate, a bounded full-name cache keyed by directory generation + exact SFN identity can remove repeated scans on revisits. Store and compare complete identity, preserve directory/file type, and publish only successful unambiguous results. Budget RAM and account for sorting/refind; a first visit still scans D entries. Do not enlarge all 512 records or bypass ambiguity checks to hide the cost.
- A sorted CUSTOM hash array plus binary search is a small bounded CPU optimization: retain all stored hashes and the subsequent exact-path open. It does not address ROM-directory search or artwork I/O; measure before prioritizing it.
- A bounded ROM-header game-code cache (directory generation + exact alias) helps revisits, not first visits, and still needs invalidation on file refresh. A broad FatFs directory-entry index or fast-open API is a larger change with identity/lifetime risk, not the first safe patch.
- The exact-99-byte flag case is a separately testable minor optimization only after validating actual truncation and CP936 handling. It is not enough to explain the reported general threshold.
