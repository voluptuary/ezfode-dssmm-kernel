## Conclusion

The active carousel renderer does not iterate over all titles. `GetEntryInfo` is direct indexed metadata access, and rest/move drawing handles three/four images. The strongest source-supported folder-size scaling candidates are name/path resolution and FatFs directory searches during synchronous incoming-artwork loading. Repeated transparency classification, copies, background preparation and presentation are real but bounded by image/screen size. These can contribute fixed latency without explaining a threshold at 60.

## Work that can scale with directories

1. `Launcher_LoadThumbDataForIndex` (`ezkernelnew.c:7870`) uses `LauncherCopyIndexedNameOrResolve` (`source/launcher_indexed_name.h`). Ordinary indexed names are copied directly. Records flagged `FM_ENTRY_ALIAS_DISPLAY` use `Launcher_ResolveIndexedName` and `Launcher_ResolveDirectoryEntry` instead. File/folder records have 100-byte filename fields (`source/ezkernel.h:23,29`); `Launcher_CopyIndexedName` sets the flag at source length >=99 bytes (`ezkernelnew.c:511`). This is a filename-length condition, not 60 entries.
2. `Launcher_ResolveDirectoryEntry` (`3839`) opens the directory and continues `f_readdir` after finding a matching name/alias, to detect ambiguity. A successful unique match scans to end. For N enumerated entries in a successful synthetic directory, the loop makes N+1 `f_readdir` calls including end-of-directory: 31/61/91/121 for N=30/60/90/120. These are analytical counts, not an executed fixture. N includes entries other than visible titles. Do not replace this with early-return on first match: that changes identity/ambiguity protections.
3. Even without explicit resolver scans, FatFs `dir_find` (`source/ff15/ff.c:2384`) rewinds via `dir_sdi(dp,0)` and walks directory records to a match/end. `follow_path` and `f_open` use this path (`3051,3742`). Constant numbers of opens do not imply constant lookup work. Missing artwork can scan a whole artwork directory; ROM header fallback can scan the ROM directory. Physical LFN records, entry position, deleted entries, clusters and cached sectors affect work. No host timing establishes SD latency.
4. Artwork order (`ezkernelnew.c:6446`) is mirrored path, named CUSTOM, GBA game-code/header fallback, extension default, then NOTFOUND. Mirrored lookup tries at most two directory spellings (`6339`); artwork-directory LFN resolution is already cached by source directory (`3913`). Its successful warm path should not be described as an unavoidable per-move parent scan. Failed resolution is not cached. Current-folder display label also has a path-keyed cache (`7476`). Recents resolve full paths and are a separate, at-most-ten-entry case.

An adjacent move with valid cache normally loads only the new incoming neighbor, not all titles. `Launcher_ShiftThumbCache` (`8470`) animates, copies retained slot data/metadata, and consumes the incoming image through `Launcher_MotionLoadIncoming` (`carousel_motion.h:549`). Animation reuses an incoming index already among the three old slots, including small wrapped lists; no second load is needed after successful motion. Initial entry and explicit jumps use `Launcher_BuildThumbCache` (`8415`) with up to three loads. Invalid pointers, invalid center or nonadjacent shifts trigger rebuild; neither rebuild nor slot count has a 60-title boundary. Leaving and revisiting an evicted neighbor requires another load; this bounded cache is not an all-title cache.

## Scheduling and ownership

- The main active browser loop waits for VBlank twice before redraw/input (`ezkernelnew.c:14874`) and scans keys after redraw (`15280`). A successful move animation presents five times, each with `VBlankIntrWait` (`carousel_motion.h:361,483`). These are explicit waits, not evidence of achieved refresh rate or exact elapsed duration.
- Incoming synchronous load occurs before the first `Launcher_MotionPollInput` (`carousel_motion.h:472,475`). Polling then occurs after each present; four key-down bitmasks can queue and releases are accumulated (`375`). A brief press/release entirely within an unpolled lookup/read can be missed. This is a scheduling risk established by call order, not a measured report of lost hardware input.
- `Launcher_ReadThumbnailBytes` (`ezkernelnew.c:6179`) reads in one call unless list-art input capture is enabled. Its chunked/polled path serves list-art capture, not carousel motion. Simply turning on list-art capture would use the wrong queue semantics (A/B only) and would still not poll inside directory search/open calls.
- `Launcher_ThumbNavRepeatDelay` (`8594`) returns zero with animations enabled. Disabled animations use 1–3 loop beats depending on view/recents/incomplete triplet (ordinary horizontal: 2; ordinary vertical full triplet: 1). Main-loop delay decrements at `15316`. No total=60 branch. Avoid blaming an extra animated repeat throttle that is not present.
- Raw carousel slots are fixed at `pReadCache+0x10036`, `+0x14C36`, `+0x19836` (`6663`), and the pointer validator requires those assignments outside list-art mode. Drawers also embed these addresses. Pointer rotation alone is therefore not a safe small optimization.
- Motion frame aliases low `pReadCache` from `+0x200`; incoming pixels and work structs alias `launcher_thumbnail_workspace`; background rows additionally use its remaining area and `pReadCache+0x1E400` (`carousel_motion.h:1–18,189`). The workspace is also used for scaled/list art. Reset/activation clears it (`ezkernelnew.c:7815,7839`). Do not retain descriptors or incoming pixel pointers there across mode transitions without ownership/invalidation rules.
- Code is recopied into sprite VRAM at `0x06014200`; sampling map is at `0x06014000`. Copies use DMA/dmaCopy and presentation explicitly uses DMA3. `UIAudio_StopForSharedBufferUse` checks active shared-buffer audio (`1403`); motion calls it before scratch use and presentation calls `UIAudio_Update`. Any code-install cache, scratch enlargement, timer instrumentation or asynchronous I/O requires separate VRAM/DMA/audio/IRQ ownership analysis.

## Low-risk potential fix and validation contract

The narrow rendering opportunity is retaining transparency classification with each raw thumbnail cache entry (including incoming), with an explicit unknown/valid state. Classify after successful load and transparency tagging, or lazily on first use; carry the state with every image copy/shift and incoming transfer. Invalidate on reset, reload/failure, folder/page/style changes and shared-buffer reuse. Keep icon transparency and NOTFOUND handling distinct, and preserve custom-origin metadata. Do not retain a pointer to motion scratch as the cache identity. This can reduce repeated scans of retained neighbors; it is **not** a demonstrated fix for the >60 symptom and should not displace lookup operation-count evidence.

For a directory-scaling fix, first count which opens/scans actually dominate the owner's folder. Bounded resolved-name/game-code reuse could help revisits but requires correct directory/style/generation identity and does not eliminate first-time incoming lookup. A complete directory index or early-exit resolver is a larger correctness change, not justified by this rendering review alone.

Validation for an implementation owner:

1. Count `GetEntryInfo`, image preparations, transparency pixels/calls, incoming loads, full rebuilds, resolver `f_readdir`, FatFs directory records, opens/read bytes and polls per move. Use N=30/60/90/120+, fixed image dimensions/content, and both short and >=99-byte names. Distinguish computed expected counts from measured host counts.
2. Separate cold entry, first step, repeated forward steps, back-and-forth eviction/reuse, held input, ten-item jumps and wrap. Test 0/1/2/3 entries too. Test horizontal/vertical, animation on/off, title/box, opaque/transparent/missing/folder art and CUSTOM Only.
3. For transparency metadata, compare pixel-identical output and scan counts before/after; exercise load failure, NOTFOUND, invalid cache, incoming reuse, style/view/page/folder changes, menu return and workspace reuse. Existing motion test stubs `MotionImage`; its pass alone cannot verify metadata or a complete move/cache lifecycle.
4. Run focused host regressions, then target build/full audit for actual code changes; inspect linked size, workspace alignment and memory layout. Do not claim timing from host elapsed time. Hardware comparison must use the same slow folder and controlled settings; timer/IRQ ownership must be established before adding timing instrumentation.

### Integration-owner proposal: existing CUSTOM manifest lookup

Follow-up inspection at owner's request: `Launcher_LoadCustomThumbManifest` / `Launcher_ShouldTryCustomThumbnail` (`ezkernelnew.c:6021–6080`) stores up to 256 hashes per style, loads once, then linearly scans the populated array for each named CUSTOM probe. This is another repeated bounded cost, proportional to CUSTOM manifest size m rather than directly to current ROM-folder count N. It does not remove FatFs opens or resolver scans.

Sorting the existing populated array once and using binary membership lookup is narrower than adding new transparency cache state: no new pixel/workspace ownership or invalidation is needed. Preserve the exact collected first-256 set, count, duplicates/collisions, style separation, absence/partial-read behavior and load-once lifetime. Sort after collecting the same set; do not alter which entries survive the cap. Use unsigned comparisons rather than subtraction that can overflow. Validate unsorted input, duplicates, 0/1/256 entries, hit/miss, high-bit hashes, style isolation and enumeration failures against current linear behavior. Warm lookup comparison count can become O(log m), but cold sorting adds work; no hardware or >60-title fix claim follows. This proposal was sent directly to the integration owner; this reviewer made no implementation changes.
